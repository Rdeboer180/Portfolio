The problem I found

A prototype that works isn't the same as one that's ready

The UI Tooling posting describes helping designers, PMs and other non-engineers build rich, reusable prototypes. Making the prototype is the easy half. The hard half is knowing whether it can move toward production: is it on approved tokens, does it have every state, can a keyboard user reach it, and has someone accountable looked at it? If a tool can't answer those, engineering rebuilds the idea from scratch and the prototype was a demo, not a decision.

How I found it

The posting, work I've done, and two gates most tools merge

  • The posting's own framing. It pairs making prototyping accessible to non-technical collaborators with connecting that work to the design system and engineering, so ideas don't stay isolated links.
  • I've built the contract side of this. In WheelRack, Tire Rack's dealer platform, I worked with a senior React engineer on 200+ tokens and 50+ Storybook components, so dependent and invalid states lived in the component, not in a comp. I've also written report-only governance skills: the agent flags drift and a person decides.
  • Mapping the flow split one gate into two. Approval is a person's judgment about behavior and access. Export is a system's guarantee about tokens. Merging them lets a sign-off wave through drift, so here they are separate, and a sign-off is pinned to the exact build it reviewed.

    The handoff

    What engineering gets with this prototype

    The prototype is the spec. Each numbered pin in the console matches a note here, and the checks run against the same rule engine and gates the console uses.

    Dev notes

    1. 1

      Builds start from a governed component, not a blank canvas

      The PM picks variants and states the component's contract allows. They can't invent a new state or a new prop, so everything they build already has a home in the catalog.

      Owned by: CATALOG.FilterChipGroup and its variants
    2. 2

      Every value traces to the token contract, or export stops

      The build lists each token it uses and where the value came from. A raw value, or a token with a changed value, is drift. Drift doesn't stop review, but it blocks export, even after sign-off.

      Owned by: rule T1 and gates().exportBlockers
    3. 3

      Six states are mandatory, and keyboard focus is one of them

      Default, selected, loading, empty, invalid and keyboard focus. A missing state, or a focus ring under 3:1 against its background, blocks approval. The reviewer can't sign off until it's fixed.

      Owned by: rules I1 and A1 and gates().canApprove
    4. 4

      Human review is its own step, pinned to one build

      A clean audit never approves anything by itself. The sign-off records the audit run it reviewed; change the brief or the build afterward and the sign-off clears, with an announcement saying why.

      Owned by: review.run compared with auditRun()
    5. 5

      The handoff is a spec, not a link

      The JSON carries the brief, the next owner, variants, states, tokens with their sources, every rule result with its evidence, the review record, and the open system questions a platform engineer would own.

      Owned by: handoff() and copyHandoff()

    Acceptance checks

    Run against

      Parity check: does the branch match the prototype?

      • The same nine rules, the same categories, and the same gate each one holds: export or approval.
      • Sign-off is refused while an approval blocker is open, and clears when the brief or build changes.
      • Export needs both a sign-off and a clean token contract; nothing else can unlock it.
      • The handoff JSON has the same top-level keys, and each rule result carries its evidence path.
      • The same aria-live text on every gate change, and no spinner motion under reduced motion.

      Engineering decides: where the rules run (in the editor, in CI, or both), how the token contract is versioned and published, and how a handoff becomes a branch. Authentication, project isolation, a durable audit log, service health and deploy reliability are platform questions I'd work through with a platform engineer, not answer alone.

      Scope

      What this is, and what I'd ask

      What it isn't

      It isn't Kyber, Airbnb's design language or any Airbnb system, and it doesn't know their interfaces. It uses generic demo tokens and a made-up component catalog, with no private APIs or assets. The rules are illustrative, the reviewer is a toggle, and the whole thing runs in this one page with no backend.

      What I'd ask the team

      1. Where do non-engineers' prototypes stall today: the build, the review, or the move into code?
      2. Which checks should run while someone builds, and which only when they ask for review?
      3. Who signs off on a prototype today, and what would make that sign-off mean something to engineering?
