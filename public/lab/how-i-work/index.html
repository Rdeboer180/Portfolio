The pitch

Prove the behavior. Scale the decision.

  • Who runs it

    I do, working directly with design and engineering. I build the prototypes, port the components, write the notes and run the checks.

    Designers keep designing in Figma. Engineers see the intent while there's still time to change it.

  • What engineering gets

    The prototype is the handoff. Each numbered note says what to build, the data rule, the motion, and one check QA can run.

    Time together goes to solving problems, so nobody has to re-explain a decision.

  • Why it works

    The connections between the teams. People share work earlier, ask better questions, and trust each other enough to push the work further.

    That is what makes the end result stronger.

How I think

Craft, systems and people

Craft

I'm a designer first and a visual problem solver, in Figma, Adobe, code or AI tools. Typography, spacing, timing and what a screen reader hears all count.

Systems

I turn a decision into a standard designers, engineers and agents can reuse. My test: does the next person have to guess?

People

I build tools and habits that help a team improve: a Figma starter template and plugins for 15+ designers, and a development program I co-founded for about 90 colleagues.

  • What does better look like?

    A mentor's question I keep by my desk. When something goes wrong, I start there.

    Then I ask what would prevent it: a clearer rule, a stronger component, better documentation, or an earlier conversation.

  • Say exactly what you want

    "Make it polished" isn't a spec. I name the component, the states, the triggers and the timing, clearly enough for a person or an agent to build from and for me to test.

    Name it, specify it, prove it in code, share what held up.

How I prototype

A static comp can show a state. Only a prototype can show the change between two of them.

  1. Question

    Name the one decision the user has to make, in their words.

  2. Constraints

    What the team has said publicly, what the platform allows, and what I can't know from outside.

  3. States

    List every state before any layout: loading, empty, error, partial, disabled, done.

  4. Build

    Working code, built from the system's real parts where I can, with fixtures for data.

  5. Check

    Keyboard, reduced motion, 320px and real failure cases, then a short note on what I'd still test.

How I build

I build with Claude Code and make the calls myself

  • Who does what

    I set the question, write the states and rules, and decide what counts as done. Claude Code builds from those notes; I run the result and send back what's wrong.

    I decide what ships.

  • Where my code is deepest

    HTML, CSS/SCSS and AEM. I wrote production Sass for 10+ reusable AEM components. On React I partnered with engineers: WheelRack's 200+ tokens and 50+ Storybook components were built with a senior React engineer.

    I say which work was direct code, agent-assisted, or a partnership.

  • The edge case that missed the point

    The first WheelRack edge case used a wheel with one size per position, so finish and size never disagreed, and that disagreement was the whole problem. I pointed it at a page with six front and four rear sizes, and the tile was rebuilt from that page's own option data.

  • The fix that passed its test and failed mine

    A scroll fix for my portfolio's card animation passed the agent's test, then broke the moment I scrolled. I reverted it the same day, asked for options, and chose the one that kept scrolling live. Testing on a phone caught a layering bug no spec mentioned.

How I hand off

What comes with every prototype

  • Numbered dev notes

    Each pin on the live prototype opens a note: the rule in testable words and the state, data or function that owns it.

    The same anatomy as WheelRack's dev notes.

  • Acceptance checks

    Given, when, then, run against the live page. They also work as eval cases for an agent.

    A failing check shows on the page.

  • A parity check and a boundary

    From an engineer's branch: "Does this match the prototype?" Each prototype also says what it leaves to engineering: architecture, data and real performance.

    Report-only. People decide which side is right.

On your team

A prototype playground between Figma and production

Two ways in, one way out. An idea starts in Figma or straight in code. Both reach production, and what's proven goes back into Figma as a component.

  • 1 · Build from real parts

    Production components are ported into a sibling repo, read-only. They keep their props, markup, ARIA and tokens; data becomes fixtures.

    A rebrand lands in the tokens, and every prototype picks it up.

  • 2 · Attach the notes

    Every state, the proposed code and the numbered notes live in one place. The designer edits the notes; review happens on a preview link.

    You can break your own prototype, never someone else's.

  • 3 · Check both ways

    Design asks "Does this match production?" Engineering asks "Does this match the prototype?"

    Every difference is a numbered note or drift to fix. Nothing else.

  • 4 · Keep what held up

    A component proven in a prototype goes back into Figma, so designers can use it next time.

    Success is fewer questions downstream.

I won't measure my success by what I can build on my own. I'll measure it by how much better we can build together.
