Presentations as a product

Draft a slide with AI, watch the system check it against its own rules, fix what fails, and only then approve it. Which rules should a deck system enforce, and which should a person decide?

What I read first

The Staff Presentation Designer posting asks you to consider presentations as a product and to establish clear governance for templates, libraries and AI-assisted workflows. This demo is my small version of that: one template set, tokens for the rules, a linter that reads them, and a human gate.

How I planned it

Question, constraints, states, build, check

  1. Question

    If non-designers (and an AI) assemble decks from a template library, which rules keep the result on-brand and readable, and where does a person still have to say yes?

  2. Constraints

    Built from public information only. No Shopify marks, colors or content; the tokens are this lab's own. Every number and sentence on the slides is synthetic. The "AI draft" is canned and offline on purpose, so the page runs anywhere and nothing is sent anywhere.

  3. States

    Clean, AI draft with violations, each rule failing alone, fixed, approved, and edited-after-approval (which revokes the approval). Audience changes the type scale, so the same slide re-checks.

  4. Build

    One slide renders from tokens (--tok-*). Six rules read the same tokens and the slide state. Fixes change tokens or content, never the checker.

  5. Check

    The acceptance list below runs live against the slide. Keyboard works end to end; the contrast check uses the WCAG formula, not a guess.

      Dev notes

      1. 1

        Rules are tokens, not paint

        Type size, color role, minimum body size and word limits live as named tokens per audience. A slide stores token names, never hex values or point sizes. Swapping the audience re-resolves every value.

        Owned by: the token file (deck.tokens.json), read by Figma variables, the Slides template and the linter
      2. 2

        One linter, six rules, plain words

        Each rule returns pass or fail, a sentence a non-designer can act on, and at most one proposed fix. The fix edits content or swaps a token; it never silences the rule.

        Owned by: the rule list; a rule is added by adding a function, not a screen
      3. 3

        AI drafts, a person approves

        Approval is only available when every rule passes. Any edit after approval revokes it and logs why. The log records who approved, not who drafted.

        Owned by: the approval state, stored with the slide

      Acceptance checks · also agent eval cases

        Parity check: does the real template match the prototype?

        • Same token names and audience scale.
        • Same six rules with the same thresholds.
        • Approval blocked on any failing rule.

        Engineering decides: where the linter runs (Figma plugin, Slides add-on, CI on exported decks) and how rules are versioned.

        Decision log

        The calls I made

        • The AI draft is canned, not live

          The point is the governance around a draft, not the model. A canned draft also makes the failures repeatable. Considered: calling a model from the page. Not worth an API key and a privacy question in a portfolio demo.

        • Audience sets the type scale

          The same slide reads differently in an executive room, an all-hands and a PDF, so the scale is a token per audience instead of a per-slide choice. Considered: one scale for everyone. It fails the back row.

        • A fix never silences a rule

          If "make it pass" can mean "turn the rule off", the system stops being governance. Considered: a per-slide override. I would add it only with a named owner and an expiry.

        • Approval belongs to a person

          The AI can draft and fix, but the gate records a human. Considered: auto-approve when clean. Taste is not a lint rule.

        Scope
        
  
        What this is, and isn't
        
  
        
    
        How it was built
        I planned and directed it with Claude Code and reviewed the code, the rules and the wording myself. Plain HTML, CSS and JavaScript, no dependencies. The contrast rule uses the WCAG relative-luminance formula.
        
    
        What it isn't
        It isn't Shopify work and uses none of Shopify's brand. It isn't a Figma plugin or a Slides add-on; it shows the rules and the gate that such a tool would carry. The content is synthetic.
        
    
        What I'd check with your team
        Which rules the Event Design team already enforces by hand, which deck mistakes cost the most review time, and where a speaker should be allowed to break the system on purpose.
